# GitLab Variables

Приложение на Go для работы с CI/CD-переменными проектов и групп GitLab. Вход по токену, поиск групп с подгруппами, переключение проектов, фильтр окружения, создание, изменение и удаление переменных. Одну переменную можно создать сразу в нескольких выбранных проектах. Интерфейс на русском, в цветах GitLab; на заставочной странице указано «Разработка Калинин И.А.».

Обычные значения видны в таблице. Для `masked` и `hidden` в таблицу передаются только свойства переменной, без значения. Маскированное значение можно показать отдельным действием на 30 секунд. Hidden-значения приложение не раскрывает: для них доступны замена значения и удаление. Видимость проекта значения не имеет. Instance-переменные в этой версии не поддерживаются.

## Запуск

Нужен Go 1.26 или новее. Внешних Go-зависимостей и сборки frontend нет.

```powershell
go run ./cmd/server
```

Откройте [http://localhost:8080](http://localhost:8080) и введите GitLab access token с областью `api`. Для работы с переменными проекта обычно нужна роль Maintainer или Owner, для переменных группы - Owner. GitLab проверяет фактические разрешения при каждом запросе. Поиск по группе показывает доступные проекты и подгруппы; наличие проекта в списке не означает права на изменение его переменных.

Для собственного GitLab задайте адрес перед запуском:

```powershell
$env:GITLAB_URL = "https://gitlab.example.com"
go run ./cmd/server
```

Токен вводится только в форме входа. Не записывайте его в конфигурацию или команды запуска. Токен с `read_api` не позволяет сохранять изменения.

## Демонстрация без токена

```powershell
$env:APP_DEMO = "true"
go run ./cmd/server
```

На странице входа появится отдельная кнопка демо-режима. Группа `platform`, две подгруппы, три вымышленных проекта и их переменные находятся в памяти. В данных есть обычные, маскированные, скрытые и многострочные переменные. Изменения видны всем демо-сессиям этого процесса и исчезают после перезапуска. Демо-режим не обращается к GitLab. Реальный вход продолжает работать отдельно.

## Отслеживаемые проекты, группы и массовое создание

При первом входе список отслеживания пуст: приложение не добавляет все доступные проекты автоматически. Найдите нужный проект или группу и явно добавьте их в отслеживание. Группа отображается деревом с подгруппами и проектами на соответствующих уровнях. Можно перестать отслеживать источник или исключить отдельный узел из дерева; это не удаляет ничего в GitLab. Выбор сохраняется отдельно для пользователя GitLab, без токенов и значений переменных.

Переменные группы редактируются в самой группе, поэтому источник изменения виден явно. Переменные, заданные на разных уровнях, не объединяются в неразличимый список. Поиск использует пагинацию GitLab и показывает доступные источники, но добавление в меню выполняется только по вашему выбору.

Для создания переменной выберите текущий проект или группу либо несколько проектов. Для нескольких проектов отметьте нужные цели и проверьте список перед сохранением. Операция ограничена 50 проектами за запрос. Каждый проект обрабатывается отдельно: результат показывает успешные создания и ошибки. Уже существующая пара `key + environment_scope` не перезаписывается. Общей транзакции и автоматического отката нет; повторный запуск выполняйте только для целей, где создание не удалось.

Для удаления предусмотрено отдельное подтверждение с ключом, окружением и проектом или группой. Удаление переменной группы влияет на наследующие её проекты; проверяйте источник перед подтверждением.

## Генератор инфраструктуры

Вкладка «Сгенерировать инфраструктуру» собирает `infrastructure` в формате проекта `ExIntegra/terraform-gitlab`: группы с родительским путём, проекты, участники групп и их роли. В политике проекта доступны основная ветка, метод слияния, создание README и правила защиты веток: push, merge, force push, включая шаблоны вроде `release/*`.

Результат обновляется после изменения полей. Можно скачать `terraform.tfvars.json`, скопировать значение `infrastructure` для Terrakube с включённым HCL либо скачать ZIP с тремя Terraform-модулями. Поддерживается загрузка существующего JSON обратно в конструктор. Черновик хранится только в памяти страницы и очищается при выходе.

Защита веток реализована в модулях из скачиваемого комплекта. В прежней схеме Terraform дополнительное поле `protected_branches` отбрасывается, поэтому для него нужен комплект или соответствующее обновление модуля проектов. Генерация не изменяет ресурсы в GitLab и не запускает Terraform. Подробности и формат - в [инструкции генератора](docs/infrastructure.md).

## Docker

Запустите Docker Desktop с Linux-контейнерами. В папке проекта выполните:

```powershell
docker compose up -d
```

Откройте [http://localhost:8081](http://localhost:8081) и введите GitLab token в форме входа. Основной `compose.yaml` скачивает опубликованный образ `exintegra/ci-variables:1.0.0` из [Docker Hub](https://hub.docker.com/r/exintegra/ci-variables); исходники и файл `.env` для запуска не нужны. Можно скопировать один `compose.yaml` в отдельную папку и выполнить ту же команду.

Управление приложением:

```powershell
docker compose ps
docker compose logs --tail=100 -f
docker compose stop
docker compose start
```

Контейнер автоматически перезапускается после перезапуска Docker, работает от пользователя `10001:10001` с корневой файловой системой только для чтения. Порт опубликован только на локальном компьютере. Настройки отслеживания сохраняются в отдельном томе `ci-variables-data`, путь внутри контейнера - `/data/tracking.json`. Логи ограничены тремя файлами по 10 МБ. Проверка работоспособности встроена в образ. После перезапуска приложения потребуется повторный вход.

Для изменения порта или адреса GitLab скопируйте `.env.example` в `.env` и отредактируйте `APP_PORT` или `GITLAB_URL`. По умолчанию внешний адрес автоматически соответствует `APP_PORT`; если `APP_ORIGIN` задан явно, он должен точно совпадать с адресом в браузере. Не записывайте токен в `.env`.

Для локальной сборки из исходников используйте отдельный override:

```powershell
docker compose -f compose.yaml -f compose.build.yaml up --build -d
```

Образ проекта в Docker Hub - `exintegra/ci-variables`, теги выпуска - `1.0.0` и `latest`, платформы - `linux/amd64` и `linux/arm64`. Для сборки и публикации предусмотрены сценарий `scripts/publish-image.ps1` и GitHub Actions. `compose.release.yaml` сохранён как совместимый вариант основной конфигурации. Обновление и перенос прежних настроек описаны в [инструкции Docker Hub](docs/docker-hub.md).

Для доступа через домен настройте HTTPS на reverse proxy и задайте `APP_ORIGIN` равным внешнему адресу, например `https://variables.example.com`. Прокси должен передавать исходный `Host`. При HTTPS сервер использует защищённую cookie. При необходимости публикации порта на другом интерфейсе измените привязку в `compose.yaml` осознанно.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `APP_ADDR` | `127.0.0.1:8080` | Адрес прослушивания сервера; в контейнере `0.0.0.0:8080` |
| `APP_ORIGIN` | `http://localhost:8080` | Точный внешний адрес приложения для проверки запросов и cookie |
| `GITLAB_URL` | `https://gitlab.com` | Единственный разрешённый экземпляр GitLab, включая при необходимости подпуть |
| `APP_DEMO` | `false` | Отдельный вход в демонстрационный режим |
| `SESSION_TTL` | `1h` | Срок сессии, от `5m` до `24h` |
| `TRACKING_FILE` | `data/tracking.json` | Настройки отслеживания; в контейнере `/data/tracking.json` |

GitLab подключается по HTTPS; HTTP допускается только для loopback-адреса при локальной разработке. Проверка TLS-сертификатов не отключается.

## Архитектура

```text
Браузер → Go HTTP API → GitLab REST API v4
               ↓
         Сессии в памяти
```

Один процесс и один исполняемый файл. Стандартная библиотека Go обслуживает API и встроенные HTML/CSS/JavaScript. GitLab остаётся источником данных; базы и копии переменных на диске нет.

- `cmd/server` - конфигурация, запуск и завершение сервера.
- `internal/app` - HTTP-обработчики, сессии, проверка запросов и изменения переменных.
- `internal/gitlab` - обращения к GitLab, проектные и групповые переменные, пагинация.
- `internal/web` - интерфейс, встроенный в исполняемый файл.
- `internal/demo` - изолированный от GitLab демонстрационный backend.

Токен хранится в серверной памяти до выхода или истечения сессии. В cookie находится случайный идентификатор сессии; JavaScript его не читает. Токен не записывается в браузерное хранилище. После перезапуска необходим повторный вход.

При редактировании сохраняется только `value`: имя, окружение, тип, маскирование, скрытость, защита и прочие свойства переменной остаются прежними. Вид ресурса, его ID и пара `key + environment_scope` определяют нужную переменную, поэтому проекты, группы и одинаковые ключи в разных окружениях не смешиваются. Перед записью или удалением сервер повторно читает переменную и проверяет её версию. Если она успела измениться, возвращается конфликт.

GitLab API не предоставляет атомарного условного обновления переменной: изменение другим клиентом в коротком промежутке между проверкой и записью всё ещё возможно. Для одной установки используйте один процесс; масштабирование на несколько реплик потребует общего хранилища сессий.

## Работа с секретами

- Списки, ответы на создание и редактирование не содержат значений `masked` и `hidden`. Сервер выполняет редактирование секретов без предварительной передачи значения браузеру.
- Раскрытие маскированного значения - отдельный POST-запрос с проверкой сессии, источника запроса, CSRF-токена и актуальности версии. В интерфейсе значение удаляется через 30 секунд, при потере фокуса, переключении ресурса и выходе.
- Приложение намеренно не показывает Hidden-значения, даже если API экземпляра GitLab возвращает их серверу. Новое значение можно записать без чтения старого.
- В запросах создания секретов передаются нужные флаги `masked` и `masked_and_hidden`; требования к длине и допустимым символам проверяет GitLab. Не отключайте маскирование ради неподходящего значения.
- Ответы имеют `Cache-Control: no-store`; токены и значения не записываются в файлы, browser storage или журналы приложения. В cookie - случайный идентификатор с `HttpOnly` и `SameSite=Strict`; для HTTPS добавляется `Secure`.
- Для доступа по сети используйте HTTPS. HTTP разрешён только на loopback при локальной работе. Не публикуйте приложение через обычный HTTP и не включайте журналирование тел запросов на reverse proxy.

Пользователь, имеющий право раскрыть секрет, может прочитать его на своём компьютере. Автоочистка интерфейса ограничивает случайное отображение и не заменяет права доступа GitLab или защиту рабочей станции.

## HTTP API

Запросы работают через серверную cookie-сессию. Для всех изменяющих запросов, включая вход, передавайте заголовок `Origin`, точно равный `APP_ORIGIN`. Для изменения данных после входа также передавайте `X-CSRF-Token`, полученный при входе. Тела запросов - JSON.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/config` | Адрес GitLab и доступность демо-режима |
| `POST /api/session` | Вход: `{"token":"…"}` |
| `GET /api/session` | Текущий пользователь и CSRF-токен |
| `DELETE /api/session` | Выход |
| `POST /api/demo-session` | Демо-вход, если включён |
| `GET /api/projects?search=&page=1` | Проекты и номер следующей страницы |
| `GET /api/groups?search=&page=1` | Поиск групп и номер следующей страницы |
| `GET /api/groups/{id}/tree` | Группа, подгруппы и все доступные проекты дерева |
| `GET /api/{kind}/{id}/variables` | Переменные ресурса с версиями; секретные значения отсутствуют |
| `POST /api/{kind}/{id}/variables` | Создание переменной |
| `PUT /api/{kind}/{id}/variables/{key}` | Изменение значения |
| `DELETE /api/{kind}/{id}/variables/{key}` | Удаление выбранного ключа и окружения |
| `POST /api/{kind}/{id}/variables/{key}/reveal` | Временное раскрытие маскированного значения |
| `POST /api/variables/bulk` | Создание одной переменной в выбранных проектах |

`kind` - строго `projects` или `groups`. Ключ в URL должен быть закодирован. При обновлении передайте `value`, `environment_scope` и `version` из последнего чтения. Для удаления и раскрытия - `environment_scope` и `version`. Создание принимает `key`, `value`, `environment_scope`, `variable_type`, `masked`, `hidden`, `protected`, `raw` и необязательный `description`. Групповые окружения могут зависеть от тарифа GitLab.

Массовое создание принимает `{"project_ids":[101,102],"variable":{…}}` и возвращает результаты отдельно для каждого проекта без секретных значений. Ошибки возвращаются как `{"error":{"code":"…","message":"…"}}`. Истёкшая сессия даёт `401`, отсутствие прав или попытка раскрыть Hidden - `403`, конфликт - `409`, ограничение частоты запросов GitLab - `429`.

## Проверки

```powershell
go test ./...
go vet ./...
go build ./cmd/server
```

Тесты используют локальный подставной GitLab и демонстрационные данные. Для проверки реального чтения и записи потребуется ваш экземпляр GitLab и токен; автоматически реальные переменные не изменяются.

Документация GitLab: [Project-level variables API](https://docs.gitlab.com/api/project_level_variables/), [Group-level variables API](https://docs.gitlab.com/api/group_level_variables/), [Groups API](https://docs.gitlab.com/api/groups/), [Personal access tokens](https://docs.gitlab.com/user/profile/personal_access_tokens/).
