# GitLab infrastructure / Terrakube

Generated by CI Variables. The structure follows ExIntegra/terraform-gitlab:
one `infrastructure` input and three modules (groups, projects, members).
This bundle additionally implements project `protected_branches` rules.

1. Put the entire bundle in a Terraform repository and select it in Terrakube.
2. Select Terraform 1.3 or newer (including 1.12.2).
3. In Terrakube workspace Variables, add the sensitive environment variable
   `TF_VAR_gitlab_token`. Enter the GitLab token there; no token is in this bundle.
4. `gitlab.auto.tfvars.json` selects the same GitLab server as CI Variables.
5. Run Init, Validate and Plan. Review the plan before Apply.

Alternatively, remove `terraform.tfvars.json` and create a Terraform variable
named `infrastructure` in Terrakube. Enable HCL and paste the generator's
Terrakube output. Use one input source to avoid file/workspace overrides.

Parent groups and usernames must already exist. Members belong to the group
and inherit access to its projects. Protection rules support branch patterns
(e.g. `release/*`); they do not create additional repository branches.
Internal visibility availability depends on your GitLab server.

The bundled provider is pinned to gitlabhq/gitlab 18.0.0. For an existing
repository, do not replace modules or the lock file blindly: this provider
differs from the earlier 3.18 version. Generate a separate workspace first,
review migration and state addresses, then run `terraform init -upgrade` and Plan.
Existing resources require import/state migration before this configuration
can manage them; the generator does not import or change live resources.

Without protected_branches, terraform.tfvars.json uses the original input
fields. For protected_branches, use this complete bundle or port that field
and its resource into the existing project module. Older object type schemas
discard unknown attributes instead of applying them.
